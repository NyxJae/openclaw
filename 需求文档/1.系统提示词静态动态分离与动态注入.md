# 需求 1：系统提示词静态/动态分离与动态注入机制

## 目标

重构 openclaw 的系统提示词架构，将真正稳定的内容与可变信息分离，通过动态注入机制实现每轮实时更新（记忆、时间、文件内容等），同时最大化保留前缀 KV 缓存，降低推理成本。

## 原则

- 真正不变或会话级不变的内容归入静态系统提示词，置于标准 `system` 角色消息中。
- 所有可能在会话过程中变化的内容归入动态系统提示词，每次循环 turn 从对应真源重新获取并作为 `user` 消息注入。
- 代码层面预留两个常量数组配置，方便后续调整哪些部分归入静态、哪些归入动态。
- Anthropic 缓存标记策略：稳定部分打标，动态部分不打标。

## 详细需求

### 1. 静态系统提示词（稳定内容）

静态部分是会话级不变的常量知识，在会话启动时构建一次，之后永不再变。

**内容清单：**

1. **身份声明** —— AI 的根身份。
2. **Safety（安全原则）** —— 宪法级行为约束，如"不追求自保、不绕过安全限制"。
3. **工具定义与调用风格** —— 可用工具的名称、一句话描述、case-sensitive 规则、调用规范、子代理规则等。
4. **OpenClaw CLI Quick Reference** —— 命令速查，纯静态知识。
5. **Skills 扫描规则** —— 扫描和使用 Skill 的方法论。
6. **Model Aliases** —— 模型别名映射，配置级，会话中不变。
7. **Workspace / Sandbox 基础路径信息** —— workspaceDir 和 sandbox 容器路径在会话中固定。只放路径元信息，**不含文件内容**。
8. **Assistant Output Directives** —— 输出格式规则（MEDIA 标签、reply tag、embed 语法等）。
9. **Silent Replies** —— HEARTBEAT_OK 和 NO_REPLY 的使用规则。
10. **文档与社区链接** —— 外部资源地址。
11. **其他纯静态知识** —— 如 Execution Bias、OpenClaw Self-Update 规则等。

**位置：** 会话首条 `system` 消息，永不变更。

**缓存标记：** 此 `system` 消息打上 Anthropic `cache_control` 标记（视为稳定前缀）。

### 2. 动态系统提示词（可变内容）

动态部分每轮 turn 从真源重新读取，作为 `user` 角色消息注入上下文。

**内容清单：**

1. **当前时间** —— 精确到分钟，本地时区（见第 4 节）。
2. **Runtime 状态** —— 当前模型、思考级别、推理模式、channel、capabilities 等。这些可能在会话中通过 `/model`、`/reasoning` 等命令切换。
3. **Project Context 文件内容** —— SOUL.md, AGENTS.md, USER.md, TOOLS.md, MEMORY.md 等文件的**完整内容**。用户可能随时编辑这些文件，必须每轮重新读取以保证实时感知。
4. **Group Chat / Subagent Context** —— 群聊上下文、引用消息、多轮对话状态等。
5. **Memory 提示词补充** —— 记忆搜索结果的注入内容。
6. **Heartbeat Section** —— heartbeat.md 的内容或默认提示。可能变化。
7. **providerDynamicSuffix** —— 供应商注入的动态后缀。
8. **Reactions 指导** —— 取决于 channel 配置，但会话中不变？**注：初期放动态，实践验证稳定后迁回静态。**

**获取时机：** 每次 turn 循环开始时，从对应真源（文件系统、配置、运行时状态）实时读取。

**注入位置：** 不再放在 `system` 角色中，而是作为一条 `user` 角色消息动态注入到上下文序列中。

**插入规则：**
- **常规情况**：找到倒数第 3 个助手消息（`assistant`），将承载动态系统提示词的 `user` 消息紧贴其**前面**插入。
  - 上下文结构示意：`sys(静态) ... user ... assistant ... user ... assistant ... [动态user] assistant ... user ... assistant`
- **早期会话**：若助手消息不足 5 条（即会话尚浅，倒数第 3 个 assistant 可能不存在或过于靠前），则将动态系统提示词 `user` 紧贴静态 `sys`，作为**第一条 user 消息**。
  - 上下文结构示意：`sys(静态) [动态user] user ... assistant ...`
- **关键约束**：插入操作不得破坏工具调用（`assistant` 含 `tool_calls`）与工具返回（`user` 含 `tool_result`）的配对关系。定位倒数第 3 个 assistant 时，需确保其不是某次 tool call 的中间节点。

### 3. Anthropic 缓存标记策略

- **所有工具的最后一个工具返回**：在其 `user` 消息上打上 `cache_control` 标记，视为稳定历史（工具定义稳定）。
- **动态系统提示词前的消息**：即紧贴动态 `user` 插入位置的前一条消息（通常是某条 `assistant` 或 `user`），打上 `cache_control` 标记，视为稳定历史边界。
- **动态系统提示词本身**：不打缓存标记（因其内容每轮可能变化）。
- **静态 system 消息**：打上 `cache_control` 标记（已在 2.1 中说明）。

### 4. 时间精度与时区

- 动态系统提示词中的当前时间，精度从原来的精确到秒/日，改为**精确到分钟**。
- 必须正确换算为用户的本地时区（ Asia/Shanghai ）。
- 时间字符串中**不显示时区偏移信息**（如 `+08:00` 或 `CST`），仅显示本地时间本身。
- 格式示例：`2026-04-26 14:35`（而非 `2026-04-26 14:35:00+08:00`）。

### 5. 代码层面配置预留

- 在源码中定义两个常量数组（或等效配置结构）：
  - `STATIC_SYSPROMPT_PARTS`：定义归入静态系统提示词的内容标识。
  - `DYNAMIC_SYSPROMPT_PARTS`：定义归入动态系统提示词的内容标识。
- 当前初始状态（按本节讨论结果）：
  - `STATIC_SYSPROMPT_PARTS`：
    ```
    ['identity_declaration', 'safety', 'tool_definitions', 'tool_call_style', 'cli_reference', 
     'skills_rules', 'model_aliases', 'workspace_base_info', 'output_directives', 
     'silent_replies', 'docs_links', 'execution_bias', 'self_update_rules']
    ```
  - `DYNAMIC_SYSPROMPT_PARTS`：
    ```
    ['current_time', 'runtime_state', 'project_context_files', 'group_chat_context', 
     'memory_supplement', 'heartbeat', 'provider_dynamic_suffix', 'reactions']
    ```
- 后续随着实践调优，可通过修改这两个数组，逐步将验证为稳定的部分从动态迁移到静态，或反之，无需改动核心注入逻辑。

## 验收标准

- [ ] 会话开始后，首条 `system` 消息包含所有静态内容（身份声明、Safety、工具定义、CLI Reference、Skills 规则、Model Aliases、基础路径信息、Output Directives、Silent Replies、文档链接等），且不再变化。
- [ ] Project Context 文件内容（SOUL.md, AGENTS.md, USER.md, TOOLS.md, MEMORY.md 等）每轮从磁盘重新读取，作为动态 `user` 消息注入。
- [ ] 每轮 turn 的动态系统提示词 `user` 消息，按规则准确插入到指定位置（倒数第 3 个 assistant 前，或早期会话时紧贴 sys）。
- [ ] 插入操作不会拆散 tool_call / tool_result 对。
- [ ] Anthropic 供应商下，静态 system、最后一个工具、动态提示词前一条消息，均正确携带缓存标记。
- [ ] 时间显示精确到分钟，为 Asia/Shanghai 本地时间，不出现时区后缀。
- [ ] 源码中存在两个可配置数组，修改其内容即可调整静态/动态分区，无需改动注入逻辑。
- [ ] 非 Anthropic 供应商（无前缀缓存机制）下，功能正常退化，不报错。
