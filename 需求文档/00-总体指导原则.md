# 00-总体指导原则

> 最后更新：2026-04-29

## 定位

本 Fork 基于 openclaw 官方仓库，在保持与上游兼容的前提下，按自身需求进行增量改造。

## 安装来源

- 本机 Gateway 安装来源：**本 Fork 仓库（NyxJae/openclaw）构建产物**
- 非 npm 官方发布包
- 上游：`openclaw/openclaw`
- 同步策略：定期 `git fetch upstream && git merge upstream/main`，有冲突时手动解决
- 升级流程：合并上游 → `pnpm build` → `npm install -g .` → `sudo systemctl restart openclaw-gateway`

## 与上游的关系

**1. 总体跟随**
- 架构、核心机制、API 设计以官方为准。
- 官方已有的功能，本 Fork 不再重复实现。

**2. 功能重叠时，以上游为准**
- 若官方后续版本实现了本 Fork 已有的类似功能，废弃 Fork 版本，迁移到官方实现。
- 保持接口和行为的向上兼容。

**3. 需求冲突时，以 Fork 为准**
- 若官方改动与 Fork 的核心需求冲突，优先保留 Fork 的行为。
- 冲突应通过适配层、配置开关或代码分支解决，而非直接放弃 Fork 需求。
- 尽量兼容上游改动，减少 merge 冲突面。

## 需求文档规范

- 每个代码项目的需求真源在项目根目录的 `需求文档/` 文件夹
- 文件命名：`序号-见名知意.md`
- 内容必须包含「举例说明」部分（输入/预期行为/反例）
- 所有实现以需求文档为准

## 技术原则

- 不破坏 upstream 可 merge 性。Fork 的改动应集中在独立模块或配置层。
- 所有改动必须有对应的需求文档编号。
- 需求文档为本 Fork 的唯一真源。
